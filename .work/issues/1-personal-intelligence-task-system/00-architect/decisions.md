# Архитектурные решения

## ADR-1: SQLite вместо PostgreSQL
**Статус**: Принято
**Контекст**: Локальная система, один пользователь, не требуется сетевой доступ.
**Решение**: SQLite — zero-конфигурация, встроенная, достаточна для тысяч записей.
**Последствия**: При масштабировании до 100к+ записей векторный поиск может замедлиться — тогда перейти на chromadb.

## ADR-2: Векторное хранение через numpy (inline)
**Статус**: Принято
**Контекст**: Необходим semantic search без внешних зависимостей.
**Решение**: Хранить embedding как BLOB (numpy float32), cosine similarity через numpy.
**Альтернатива**: chromadb — rejected (избыточно на старте, лишняя зависимость).
**Последствия**: При >1000 записей — заменить на faiss или chromadb.

## ADR-3: Ollama API как primary LLM
**Статус**: Принято
**Контекст**: Локальный AI, конфиденциальность, скорость.
**Решение**: Ollama REST API (http://localhost:11434/api/generate).
**Альтернативы**:
- LM Studio API — fallback
- OpenAI API — rejected (нарушает локальность)
**Последствия**: Пользователь должен иметь Ollama с моделью (llama3, mistral).

## ADR-4: FastAPI для API
**Статус**: Принято
**Контекст**: Необходим лёгкий, быстрый REST API.
**Решение**: FastAPI + uvicorn.
**Альтернатива**: Flask — rejected (медленнее, нет автовалидации).
**Последствия**: Автоматическая документация через /docs.

## ADR-5: Изоляция модулей через интерфейсы
**Статус**: Принято
**Контекст**: Каждый агент — отдельная ответственность.
**Решение**: Модули общаются через Memory Core (единая точка данных). Analyzer не пишет в БД.
**Последствия**: Сложнее сделать прямой путь, но легче отлаживать и тестировать.

## ADR-6: Nirvana Integration через внешний MCP
**Статус**: Принято
**Контекст**: Nirvana Bridge уже существует как MCP-сервер.
**Решение**: Decision Engine формирует JSON → внешний вызов Nirvana Bridge MCP.
**Последствия**: PITS не зависит от реализации Nirvana.

## ADR-7: Confidence thresholds с возможностью настройки
**Статус**: Принято
**Контекст**: Разные пользователи — разный уровень автоматизации.
**Решение**: Пороги (85/50) вынесены в config; пользователь может менять.
**Последствия**: Гибкость без изменения кода.

## ADR-8: Единый конфигурационный файл YAML
**Статус**: Принято
**Контекст**: Все настройки системы в одном месте.
**Решение**: config/config.yaml — Ollama URL, пути, пороги, модель.
**Последствия**: Простота настройки для пользователя.

## ADR-9: Тесты через pytest с SQLite :memory:
**Статус**: Принято
**Контекст**: Быстрые, изолированные тесты без влияния на данные.
**Решение**: pytest + in-memory SQLite для каждого теста.
**Последствия**: Тесты не зависят от окружения.

## ADR-10: Logging через стандартный logging
**Статус**: Принято
**Контекст**: Необходимы логи для отладки и аудита.
**Решение**: logging + ротация файлов, отдельный лог для каждого модуля.
**Последствия**: Простота, без внешних зависимостей.
