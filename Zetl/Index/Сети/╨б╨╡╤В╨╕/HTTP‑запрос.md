
HTTP‑запрос — это цепочка шагов от пользователя до сервера и обратно. Ниже краткая, но полная схема пути.

---

## Шаги запроса

1. Пользователь вводит URL или кликает ссылку.
2. Браузер проверяет кэш (DNS, HTTP, Service Worker).
3. Если IP неизвестен — выполняется DNS‑разрешение имени.
4. Устанавливается соединение:
   - TCP 3‑way handshake для HTTP/1.1 и HTTP/2.
   - Для HTTPS дополнительно TLS‑рукопожатие.
   - Для HTTP/3 используется QUIC (UDP).
5. Формируется HTTP‑запрос (метод, путь, заголовки, тело).
6. Запрос проходит через прокси, балансировщики и межсетевые экраны.
7. Сервер получает запрос и передаёт его приложению.
8. Приложение обращается к БД/кэшу/другим сервисам.
9. Сервер формирует HTTP‑ответ (статус, заголовки, тело).
10. Ответ возвращается клиенту, сохраняется в кэше (если можно).
11. Браузер рендерит результат.

---

## Подробный путь (пример: google.com)

1. Пользователь вводит `https://google.com`.
2. Браузер проверяет кэш страницы и DNS‑кэш браузера.
3. ОС проверяет локальный DNS‑кэш и `hosts`.
4. Если IP нет — запрос уходит на рекурсивный DNS (обычно у роутера/провайдера).
5. Рекурсивный DNS запрашивает корневые сервера, затем TLD (`.com`), затем авторитетные сервера домена и возвращает IP.
6. Браузер инициирует соединение на **L4**: TCP (HTTP/1.1/2) или QUIC (HTTP/3).
7. Для HTTPS выполняется TLS-handshake: клиент и сервер согласуют параметры шифрования, сервер предъявляет сертификат, клиент проверяет домен (SAN/CN) и цепочку доверия до CA, после чего устанавливаются сессионные ключи и дальше HTTP идёт внутри TLS.
8. На **L7** формируется HTTP‑запрос: метод, путь, заголовки, cookies, тело.
9. Пакеты проходят через локальный роутер, NAT, провайдера, магистральные сети, балансировщики.
10. На сервере запрос принимает веб‑сервер, передаёт приложению, используются кэши/БД.
11. Сервер формирует HTTP‑ответ и отправляет обратно.
12. Браузер получает ответ, применяет политики кэша, рендерит DOM/CSS/JS.

---

## Что происходит при HTTPS

- Клиент проверяет сертификат сервера.
- Согласуются параметры шифрования.
- Дальше весь HTTP трафик идёт внутри TLS.

---

## Частые узкие места

- Медленный DNS.
- Долгий TLS‑handshake.
- Низкая пропускная способность.
- Долгое время ответа сервера.

---

## On-call диагностика (сценарий -> проверка)

Симптом: «сайт медленно открывается».

Проверки по слоям:
```bash
# DNS
dig +stats example.com

# TCP/TLS
curl -sv -o /dev/null https://example.com

# HTTP тайминги
curl -s -o /dev/null -w 'dns=%{time_namelookup} connect=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' https://example.com

# маршрут
traceroute example.com
```

Как интерпретировать:
- большой `time_namelookup` -> проблема DNS;
- большой `time_appconnect` -> проблема TLS/сети до edge;
- большой `time_starttransfer` при нормальном TLS -> проблема backend/app.

## Собес фокус

- Объяснить полный путь запроса: browser cache -> DNS -> TCP/TLS -> HTTP -> app -> response.
- Показать, на каком шаге работает каждый слой OSI.
- Объяснить разницу HTTP/2 (TCP) и HTTP/3 (QUIC/UDP) в контексте задержек.

---

## Типовые ошибки

- Поиск проблемы только в приложении без проверки DNS/TLS/маршрута.
- Неверная интерпретация TTFB как «всегда проблема сети».
- Отсутствие correlation id между edge и backend логами.

---

## Мини-лаба (15-30 минут)

1. Измерь тайминги `curl -w` для одного URL в норме.
2. Подмени DNS на медленный резолвер и сравни `time_namelookup`.
3. Искусственно замедли backend endpoint и сравни `time_starttransfer`.
4. Зафиксируй: какой сигнал показывает какой слой.
