DNS (Domain Name System) — система, которая преобразует доменные имена в IP‑адреса и обратно.

---

## Зачем нужен

- Позволяет использовать удобные домены вместо IP.
- Централизует управление адресами сервисов.

---

## Как работает запрос

1. Клиент проверяет локальный кэш (браузер/ОС).
2. Если нет — обращается к рекурсивному DNS‑серверу.
3. Рекурсор спрашивает корневые серверы.
4. Затем сервер зоны (например, `.ru`).
5. Затем авторитетный сервер домена.
6. Возвращается IP‑адрес и сохраняется в кэше на время TTL.

---

## Важные концепции из Таненбаума (2023)

- **Рекурсивный vs итеративный запрос**: клиент обычно делает рекурсивный запрос своему резолверу, а резолвер дальше идет итеративно по иерархии DNS.
- **Авторитетный сервер** отвечает за конкретную зону и является источником истины.
- **Кэширование** включает не только успешные ответы, но и negative caching (NXDOMAIN).
- **Anycast DNS** снижает задержку и повышает устойчивость резолвинга.

## Типы записей

- **A** — IPv4 адрес.
- **AAAA** — IPv6 адрес.
- **CNAME** — псевдоним.
- **MX** — почтовые серверы.
- **NS** — серверы зоны.
- **TXT** — текстовые записи (SPF, DKIM, валидация).
- **PTR** — обратное разрешение IP → домен.

---

## Частые проблемы

- Неверный TTL — долгое обновление.
- Кэш «держит» старые записи.
- Проблемы с NS или делегированием.

## Диагностика DNS

Основные утилиты:

- `dig` — основной инструмент, даёт полный ответ.
- `nslookup` — проще, но менее информативен.

Примеры:

```bash
dig example.com
dig example.com @8.8.8.8
nslookup example.com
dig +trace example.com
```

## On-call диагностика (пошагово)
1. Проверить, что проблема именно в DNS, а не в сети:
```bash
ping -c 2 1.1.1.1
```
2. Проверить резолв через системный резолвер:
```bash
getent hosts example.com
```
3. Проверить авторитетный/внешний резолвер:
```bash
dig +short example.com @8.8.8.8
dig +trace example.com
```
4. Проверить TTL и тип записи:
```bash
dig example.com A +noall +answer
dig example.com AAAA +noall +answer
dig example.com NS +noall +answer
```

## Типовые ошибки
- Изменили A-запись, но забыли про высокий TTL.
- CNAME указывает на несуществующую цель.
- NS/делегирование зоны не совпадают у регистратора и DNS-провайдера.
- Нет fallback DNS в конфигурации узлов.
- Попытка сделать CNAME на apex-домене (ограничение DNS-практики у многих провайдеров).
- Кэш NXDOMAIN «держит» старое состояние после исправления записи.

## Мини-лаба (15-30 минут)
1. Создай тестовый домен/запись и выставь TTL 300.
2. Проверь ответ через 2 разных резолвера.
3. Измени запись, сравни поведение кэша до и после TTL.
4. Удали запись на короткое время и проверь negative cache поведение.
