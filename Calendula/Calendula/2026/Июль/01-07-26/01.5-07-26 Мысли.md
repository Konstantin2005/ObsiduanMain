### [[JVM]]
То есть JVM — это переводчик между человеком и Процессором?
Да. Вот это самое удачное объяснение.
Только есть один нюанс.
JVM переводит **не Java**, а **Bytecode**.
Почему JVM сама ускоряет программу?
Потому что она во время работы видит, какие методы вызываются чаще всего.
И может сказать:
 "Этот метод вызывают уже миллион раз. Я один раз переведу его в машинный код, чтобы больше не переводить."
Это и есть JIT.
Можно ли вынести GC и потоки в отдельную программу?
Практически нет.
Представь, что есть отдельная программа "GC".
Она должна понять, какие объекты больше не используются.
Но объекты находятся внутри памяти JVM.
Получается, ей пришлось бы постоянно спрашивать JVM:
 "А этот объект еще нужен?"
 "А этот?"
 "А этот?"
Это было бы медленнее, чем если GC находится внутри JVM и сразу видит всю память.


### [[JRE]]
JRE — это среда выполнения Java. Сейчас почти не используется отдельно, так как входит в JDK.
**То есть JRE нужен только пользователям?**
Да.
Разработчик → JDK.
Пользователь → раньше JRE.
Сейчас обычно все используют JDK.


### [[точка class]]
`.class` — это контейнер.
Внутри него лежит Bytecode, а еще служебная информация:
- имя класса;
- список полей;
- список методов;
- константы (Constant Pool);
- аннотации;
- информация для JVM.
То есть `.class` ≠ только Bytecode.


### [[ByteCode]]
Промежуточный код который используется для JVM который компилируется .javac для того чтобы уже JVM перевела этот код на нужную опперационку.




### [[Интерпритатор]]
Компонент JVM который сразу выполняет ByteCode не доходя до машинного кода, чтобы как можно быстрее запустить работу. Он работает совместно с JIT как тимейты. JIT помогает ему компилировать много повторяющие методы.

### [[JIT]]
штука для ускорения программы и ее работы. Этот кусок работает как локальный компилятор который компилирует частые Горячие методы то есть методы которые много раз повторяются. И вместо интеритации ByteCode использует уже скомпилированный код. Что хорошо оптимизирует работу.
